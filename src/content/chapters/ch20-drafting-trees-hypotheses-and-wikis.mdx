## Passing viewer selections and Derived inputs

When the Record Agent built **Study A (`261015A`)** through `ELNCommunityMCP.exe` (`tribo_study/reports/record_report.md`), it had to handle two things beyond plain key extraction: viewer evaluation selections and multi-input `Derived` formulas.

First, on `Thickness 261015A` (`eln://item/3`), scan `3.fibps` had a clean automatic step, while `1.fibps` and `2.fibps` needed the standard left and right pixel rectangles (`rect_a` $= [69, 80, 208, 403]$ and `rect_b` $= [347, 80, 486, 403]$ on the $556 \times 484$ pixel map). In MCP, `extract_file_key_values` accepts an optional `selection` parameter (`rect_a`, `rect_b`, `pix_w`, and `pix_h`) for that call. When `selection` is passed, `aps.fibps` (version 3) computes `Step Height` and `Step Height STD` from those exact rectangles and returns an `analysis_snapshot` object with `"mode": "regions"` and the rectangle coordinates. Similarly, on `BN-DLC.zrw` (`file_id = 5`), `aps.zrw` returns an `analysis_snapshot` recording the plateau cycle interval and file hash, and on `BN-DLC(261015A).mit` (`file_id = 4`), `aps.mit` returns an `analysis_snapshot` recording the 9 evaluated indents.

The agent passes that `analysis_snapshot` object **unchanged** into `add_values`. Because the snapshot is stored on the value, running `check_value_drift` later replays those exact rectangles, indents, or cycles without opening the GUI.

Second, after storing the three `Wear Area` values (`value_id = 21, 22, 23` on `Wear track 261015A`) and `Fn` (`value_id = 15`) and `Cycles` (`value_id = 16`) on `Friction test 261015A` (`eln://item/5`), the agent calls `add_derived_value` with `formula_id: "wear_rate_reciprocating"` and `inputs: {"area": [21, 22, 23], "normal_force": 15, "cycles": 16}`. The server averages the three `Wear Area` inputs, calculates $K = A / (2 \cdot F_n \cdot N) = 3.05 \times 10^{-7}\,\text{mm}^3/(\text{N}\cdot\text{mm})$, and stores `value_id = 24` with source kind `Derived` and all five input value IDs:

>
> **Assistant:** Stored all three step heights, the three wear areas, and the derived wear rate for sample `261015A`:

## Updating and removing values and files safely

When you extract values interactively in the Desktop viewer (<a href={`${import.meta.env.BASE_URL}/ch9-values-units-formulas-and-provenance#reader-mappings-unit-factors-and-standard-deviations`}>Chapter 9: Reader mappings, unit factors, and standard deviations</a>), re-extracting from the same file updates the existing `Reader` value in place. The MCP write tools behave differently by design:

<Warning title="add_value and add_values in MCP always insert new rows">Calling `add_value` or `add_values` through MCP always creates a new value record; it never overwrites an existing `Reader` value from the same file and key. If you need to update an existing value in place (for example, after a reader version upgrade) or remove obsolete values, use `update_value`, `remove_value`, or `remove_values` instead of calling `add_values` a second time.</Warning>

APS ELN provides four dedicated MCP tools for maintaining existing values and files (<a href="#table-20-1">Table 20-1</a>):

- **`update_value`:** takes `value_id` and updates one or more of `value`, `tolerance`, `description`, `rec_type`, `value_type_id`, and (for a `Reader` value) `reader_version` and `analysis_snapshot`. It preserves the old fields in the audit log (`entity_type: "Value"`) and returns them in `previous`, alongside any `dependent_derived_value_ids` that use this value as an input. (The number of a `Derived` value cannot be edited with `update_value`; call `add_derived_value` to compute a new one.)
- **`remove_value` and `remove_values`:** hard-delete one value or up to 200 values in an all-or-nothing transaction. They record an optional `reason` along with the old value, tolerance, type, and source in the owning item's audit log.
- **`delete_file`:** permanently deletes an attached file and all `Reader` values extracted from it (leaving `Manual` and `Unknown` values intact). By default, `dry_run` is `true`, so your first call previews `values_to_delete` without deleting anything; to execute the deletion, pass `dry_run: false` and `confirm_hash` (the file's MD5 hash from `list_files`).

All four tools refuse to touch signed items, deleted items, or records attached to or cited by a hypothesis in `InReview` or `Accepted`.

> **You:** We re-extracted `Hardness` and `Modulus` on `Indentation 261015A` after upgrading `aps.mit` to version 2. Update the two stored values in place so their `reader_version` and 9-indent `analysis_snapshot` are current without creating duplicate rows.
>
> **Assistant:** Updated both values in place on `Indentation 261015A` (`eln://item/4`) via `update_value` (previous state preserved in the `Value` audit log; `dependent_derived_value_ids: []`):
> - **Hardness (`value_id = 13`):** $5.92 \pm 0.47\,\text{GPa}$ (`Reader` `aps.mit` v2, `file_id = 4`, `mode: "automatic"` over 9 indents).
> - **Modulus (`value_id = 14`):** $127.17 \pm 11.06\,\text{GPa}$ (`Reader` `aps.mit` v2, `file_id = 4`, `mode: "automatic"` over 9 indents).

## Drafting and updating Wiki pages

You can also use an AI assistant to turn raw project data and literature notes into Project Wiki pages (<a href={`${import.meta.env.BASE_URL}/ch13-project-wiki-notes-tags-and-links#the-five-section-project-wiki`}>Chapter 13: The five-section Project Wiki</a>):

- **`wiki_create_page`:** takes `project_id`, `section` (`Goals`, `Ideas`, `Literature`, `Analysis`, or `References`), `title`, `body_md`, and optional `attachments` (paths inside `--upload-root`). It idempotently creates the `Wiki/` and `Wiki/<section>/` folders if they do not exist yet, creates the `Wiki` item, and writes the `.md` body and any attachments.
- **`wiki_get_page`:** downloads the page's `.md` body and returns it inline as UTF-8 `body_md` along with item metadata and non-Markdown attachment records.
- **`wiki_update_page`:** replaces `body_md` in place and optionally uploads additional attachments.

Both `wiki_create_page` and `wiki_update_page` are **all-or-nothing**. They validate every file type and upload-root path before writing; if any step fails, they roll back the new records and restore the previous `.md` body text automatically.

> **You:** Create a Wiki page in the `Analysis` section of the Study A project summarizing the mechanical and tribological properties of sample 261015A with clickable links to each measurement item.

> **Assistant:** Created Wiki page **`BN/DLC 261015A Tribology Summary`** (`eln://item/7` under `Wiki / Analysis` in `Tribo study: BN/DLC coating (demonstration)`) with live record links:

## Drafting experiment series and preparing hypotheses

Two high-level planning features in APS ELN follow the same human-in-the-loop pattern: **Experiment Series** (<a href={`${import.meta.env.BASE_URL}/ch12-experiment-series-and-taguchi-arrays#planning-a-series-in-the-series-window`}>Chapter 12: Planning a series in the Series window</a>) and **Hypotheses** (<a href={`${import.meta.env.BASE_URL}/ch11-the-hypothesis-tree-and-evidence#why-connect-experiments-to-a-hypothesis-tree`}>Chapter 11</a>). Your AI assistant can draft the plan or prepare the evidence through MCP. Starting the series, linking depositions, confirming planned values, and closing or approving hypotheses stay with you in the Desktop GUI (<a href="#fig-20-1">Figure 20-1</a> and <a href="#table-20-1">Table 20-1</a>).

For an **Experiment Series**, MCP provides two write tools:

- **`create_series`:** takes `project_id`, `title`, and optional `purpose`, `factors` (`1` to `7` objects with `value_type_id`, `label`, `range_min`, `range_max`, and `levels`), `fixed`, `responses`, `design` (`"grid"`, `"taguchi"`, or `"manual"`), `points`, and `target_folder_id`. When you pass `levels` on every factor without specifying `design`, the server uses `"grid"` for 1 or 2 factors and `"taguchi"` for 3 to 7 factors (<a href={`${import.meta.env.BASE_URL}/ch10-principles-of-experiment-planning#sweeps-full-grids-and-taguchi-orthogonal-arrays`}>Chapter 10</a>). It creates the series in **`Draft`** status and returns `series_id`, `status`, `point_count`, and `taguchi_array` (such as `"L9"`). You then review the plan in **Project > Series...** and click **Start** when ready.
- **`update_series_plan`:** takes `series_id` and updates `purpose`, `factors`, `fixed`, `responses`, `target_folder_id`, `design`, or `add_points` (with an optional `reason`). While a series is `Draft`, any plan field can be updated; once you click **Start** in the Desktop GUI (`Active`), MCP can only update `purpose` and append new points. Starting a series, making or linking depositions, and confirming `planned` values are always done by a person in the Desktop GUI.

For a **Hypothesis**, MCP always uses the stored JSON status names (`Proposed`, `Approved`, `InReview`, `Accepted`, `Rejected`, `Abandoned`), while the Desktop window shows edition-specific labels (<a href={`${import.meta.env.BASE_URL}/ch11-the-hypothesis-tree-and-evidence#table-11-1`}>Chapter 11: Table 11-1</a>). An agent can prepare every step between the two human decisions:
1. **Propose (`propose_hypothesis` and `update_hypothesis`):** the agent creates a root or child hypothesis (`statement` and `change`) in `Proposed` (Community: `Draft`; Team: `Proposed`).
2. **Wait for the first human decision in the GUI:** in Community, click **Start** in the **Hypotheses** window to make the draft `Open`; in Team mode, a reviewer clicks **Approve**.
3. **Attach runs and cite evidence (`attach_run` and `cite_evidence`):** once the hypothesis is `Approved` (`Open`), the agent attaches `Run` or `Reference` items and cites key items, files (`file_id`), or values (`value_id`). The server refuses a `Run` from another project (`[run_other_project]`), refuses an item outside an attached run (`[not_citable]`), and refuses an unconfirmed `Planned` value (`[planned_value]`). Valid citations snapshot the file's MD5 hash or the value's stored number and bump the hypothesis `version`.
4. **Submit the conclusion (`submit_conclusion`):** the agent calls `get_hypothesis` to read the current `version`, then calls `submit_conclusion` with the Markdown `conclusion` (including `[[item:N]]` links), `outcome` (`Supported`, `Refuted`, or `Inconclusive`), and `version`. The status becomes `InReview` (Community: `Open · conclusion ready`; Team: `In review`).
5. **Wait for the final human decision in the GUI:** inspect the cited curves and values in the **Hypotheses** window, then click **Close** (Community) or **Accept** (Team) to seal the conclusion.

> **You:** I approved the hypothesis on sample 261015A in Desktop. Attach `Deposition 261015A` as its experimental run, cite the indentation hardness, steady-state COF, and derived wear rate as evidence, and submit the conclusion as `Supported` for my final review.
>
> **Assistant:** Attached the run, recorded the three snapshot-hashed citations, and submitted the conclusion on hypothesis **`DLC top-layer wear protection on 46-period BN/DLC`** (`hypothesis_id = 1`, now in `InReview` / `Needs acceptance`, `version = 5`):
> - **Attached Run:** `Deposition 261015A` (`eln://item/1`, role `Run`).
> - **Cited Evidence:** `Hardness` $= 5.92 \pm 0.47\,\text{GPa}$ (`value_id = 13` on `[[item:4]]`), `COF` $= 0.528 \pm 0.019$ (`value_id = 17` on `[[item:5]]`), and `Wear rate` $= 3.05 \times 10^{-7}\,\text{mm}^3/(\text{N}\cdot\text{mm})$ (`value_id = 24` on `[[item:5]]`).
