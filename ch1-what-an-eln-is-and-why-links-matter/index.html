Part 1 · Chapter 1

What an ELN Is, and Why Links Matter

In This Chapter

  • Tracing the four links from a physical sample to a published number
  • Seeing how a notebook can keep every file and still lose the link to its numbers
  • Following the four rules that keep your data trail unbroken
  • Viewing the complete student workflow on one page

When you put a number into a thesis table or a journal figure, someone will eventually ask where it came from. Perhaps your supervisor asks why one coating wore through twice as fast as another. Perhaps a reviewer asks how many indents were averaged in your hardness value, or which period thickness came out of your X-ray reflectivity fit. An electronic laboratory notebook (ELN) does its job when you can answer that question in seconds without guessing.

The four links in every laboratory result

Every experimental number depends on four linked records (Figure 1-1):

  1. The Sample (Specimen): the physical piece or model you made, identified by its sample code (such as 261015A).
  2. The Operation (Procedure or Action): what you did to that sample, such as a sputter deposition, a 3D profilometer scan, a nanoindentation series, or a friction test.
  3. The Raw File: the unaltered file written by the instrument (.depo.json, .fibps, .mit, .zrw, .xrdml) or by an analysis program (.xrcx).
  4. The Stored Number (Value): the quantity, numerical value, unit, and tolerance saved on the procedure or action (for example, an indentation hardness of 5.92±0.47 GPa5.92 \pm 0.47\,\text{GPa}5.92±0.47GPa).

In APS ELN, the first three links are structural. You create an Action under a Specimen and attach the instrument file to that action. The tree then records which sample was measured, which operation ran, and where the raw bytes are stored.

Why the fourth link is the one that breaks

Most students keep the first three links without even trying. You create a folder for your sample, drop your measurement files inside it, and move on. Weeks later, when you write a report or prepare a presentation, you open those files, calculate an average or run a fit, and type the final number into a table.

Six months later, that fourth link is gone:

  • A number was typed by hand (Manual source) with no link to its file. Nobody can tell which .mit or .fibps file produced it, which outliers were excluded in the viewer, or whether a unit conversion was done in someone’s head.
  • A screenshot was saved instead of the raw data. A .png of a fit window looks convincing on screen, but no reader plugin can extract numbers from it or re-verify the fit.
  • An evaluation window or reader changed. Perhaps you changed the cycle range on a friction curve or updated a reader plugin. The stored number still shows the old value, and nothing warns you unless the notebook recorded the file hash and reader version when the number was extracted.

Warning: typing numbers by hand

When you type a result by hand (Manual source) instead of extracting it from the attached file (Reader source), APS ELN cannot check that number later. If a reader version, calibration, or evaluation window changes, a Manual number stays unverified. Use Extract Values whenever a reader supports your file format.
Going Deeper: how APS ELN stores value-level provenance

Starting in APS ELN 2.1 (notebook format 5 in Community), every stored value carries a structured source record:

  • Reader: records the file_id, the file’s MD5 hash at extraction time, the reader_id (such as aps.mit or aps.xrcx), and the integer reader_version. It also stores the emitted key name, the emitted unit, and the conversion factor, plus an optional analysis snapshot (such as ticked .mit indents or a .zrw cycle interval).
  • Derived: records the formula_id (such as wear_rate_reciprocating), the formula_version, and the exact value_id list of the stored input values used in the calculation.
  • Manual: records that a person typed or edited the number. If you edit the number or tolerance of a Reader or Derived value by hand, its source switches to Manual while preserving the previous reader or formula note.
  • Unknown: marks legacy values created before format 5 source tracking existed.

Two running examples: Study A and Study B

  • Study A (261015A, a BN/DLC tribological coating): A sputter deposition (Deposition 261015A) produces specimen 261015A. You measure it in three actions directly under the specimen: Thickness 261015A (1.fibps–3.fibps), Indentation 261015A (BN-DLC(261015A).mit), and Friction test 261015A (BN-DLC.zrw). A child action under the friction test, Wear track 261015A, holds three optical profiler scans across the wear scar (wear 1.fibps–wear 3.fibps). The finished record has 11 raw files, 23 Reader values, and 1 Derived wear-rate value.
  • Study B (261014B, a Co/C multilayer X-ray mirror): A sputter deposition (Deposition 261014B) includes a plasma cleaning action (Cleaning 261014B) and produces specimen 261014B (20 periods of cobalt and carbon on soda-lime glass). Under the specimen sit the X-ray reflectivity scan XRR-1 261014B (XRR-1_Co-C(261014B).xrdml) and its child analysis action XRR fit 261014B (XRR-fit_Co-C(261014B).xrcx). The finished record has 8 files and 22 Reader values.

Chapter 4: Your First Sample Record in Twenty Minutes builds Study A step by step in the Desktop window. Chapter 17: Study B: XRR Fitting with Provenance builds and fits Study B with the MCP server and X-Ray Calc 3.

Four rules that keep your data trail unbroken

Four habits prevent these broken links in daily work:

  1. Build the whole item tree at the start of the run. Create the Procedure, the Specimen, and every planned Action before you walk to the instruments. An empty action in the tree reminds you that a file is still missing. At the end of the experiment, no action should remain empty.
  2. Attach the raw instrument file, never a screenshot. A .png screenshot of an XRR fit or an indentation curve cannot be re-analyzed or checked for drift. It also gives zero values to a reader. Always attach the native file (.depo.json, .tsv, .fibps, .mit, .zrw, .xrdml, .xrcx).
  3. Keep result numbers out of file names. Name a file after the sample code, the measurement type, and the position or counterbody, such as BN-DLC(261015A).mit or wear 1.fibps. Never name a file 351.9nm.fibps. Results belong in stored Values, where they carry units, tolerances, and provenance.
  4. Extract values from files instead of typing them. Click Extract Values in the viewer so every number carries its Reader source. For multiple files, right-click the files and choose Extract values from N files…. Use Add > Derived Value… for formula outputs.

Remember

A file name tells you which sample and which spot was measured. A stored Value tells you what number the measurement gave.

In ELN

To check where any stored number came from, open the Procedure or Action with Item > Edit, select the Values tab, and click the value row. The line below the list names the reader, its version, the key name, and the source file, and enables Go to file.
