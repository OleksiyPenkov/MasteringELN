Part 4 · Chapter 18

Drafting Trees, Hypotheses, and Wikis

In This Chapter

  • Passing viewer selections (selection) and analysissnapshot in Study A (261015A)
  • Computing Derived values (addderivedvalue) and editing values safely via MCP
  • Drafting and updating Project Wiki pages (wikicreatepage, wikiupdatepage)
  • Proposing hypotheses and citing evidence via MCP while keeping approvals in the GUI

In Chapter 17, every extracted value in Study B (261014B) came straight from a file’s default reader output. Sometimes an agent also needs to extract a step height from specific pixel rectangles on a .fibps map, or compute a Derived wear rate from three wear-track scans. You can also ask it to update a value after a reader upgrade, write a Project Wiki page, or prepare a hypothesis with cited evidence while leaving approvals and signatures to you in the Desktop GUI (Figure 18-1).

Passing viewer selections and Derived inputs

When the Record Agent built Study A (261015A) through ELNCommunityMCP.exe (tribo_study/reports/record_report.md), it had to handle two things beyond plain key extraction: viewer evaluation selections and multi-input Derived formulas.

First, on Thickness 261015A (Item 3), scan 3.fibps had a clean automatic step, while 1.fibps and 2.fibps needed the standard left and right pixel rectangles (rect_a and rect_b on the 556×484556 \times 484556×484 pixel map). In MCP, extract_file_key_values accepts an optional selection JSON object for that call:

{
  "file_id": 6,
  "selection": {
    "rect_a": [69, 80, 208, 403],
    "rect_b": [347, 80, 486, 403],
    "pix_w": 556,
    "pix_h": 484
  }
}

When selection is passed, aps.fibps (version 3) computes Step Height and Step Height STD from those exact rectangles and returns an analysis_snapshot object with "mode": "regions" and the rectangle coordinates. Similarly, on BN-DLC.zrw (file_id = 5), aps.zrw returns an analysis_snapshot recording the plateau cycle interval and file hash, and on BN-DLC(261015A).mit (file_id = 4), aps.mit returns an analysis_snapshot recording the 9 evaluated indents.

The agent passes that analysis_snapshot object unchanged into add_values. Because the snapshot is stored on the value, running check_value_drift later replays those exact rectangles, indents, or cycles without opening the GUI.

Second, the agent stores the three Wear Area values (value_id 21, 22, and 23 on Wear track 261015A) and Fn (value_id 15) and Cycles (value_id 16) on Friction test 261015A (Item 5). It then computes the reciprocating wear rate by calling add_derived_value:

{
  "item_id": 5,
  "formula_id": "wear_rate_reciprocating",
  "inputs": {
    "area": [21, 22, 23],
    "normal_force": 15,
    "cycles": 16
  }
}

The server averages the three Wear Area inputs, calculates K=A/(2⋅Fn⋅N)=3.05×10−7 mm3/(N⋅mm)K = A / (2 \cdot F_n \cdot N) = 3.05 \times 10^{-7}\,\text{mm}^3/(\text{N}\cdot\text{mm})K=A/(2⋅Fn​⋅N)=3.05×10−7mm3/(N⋅mm), and stores value_id = 24 with source kind Derived and all five input value IDs (21, 22, 23, 15, 16).

Remember

Never pass a value field to add_derived_value. The server calculates the number from the stored input values and refuses any call that tries to supply the result number from the client.

Updating and removing values and files safely

When you extract values interactively in the Desktop viewer (Chapter 9: Reader mappings, unit factors, and standard deviations), re-extracting from the same file updates the existing Reader value in place. The MCP write tools behave differently by design:

Warning: add_value and add_values in MCP always insert new rows

Calling add_value or add_values through MCP always creates a new value record; it never overwrites an existing Reader value from the same file and key. If you need to update an existing value in place (for example, after a reader version upgrade) or remove obsolete values, use update_value, remove_value, or remove_values instead of calling add_values a second time.

APS ELN provides four dedicated MCP tools for maintaining existing values and files (Table 18-1):

  • update_value: takes value_id and updates one or more of value, tolerance, description, rec_type, value_type_id, and (for a Reader value) reader_version and analysis_snapshot. It preserves the old fields in the audit log (entity_type: "Value") and returns them in previous, alongside any dependent_derived_value_ids that use this value as an input. (The number of a Derived value cannot be edited with update_value; call add_derived_value to compute a new one.)
  • remove_value and remove_values: hard-delete one value or up to 200 values in an all-or-nothing transaction. They record an optional reason along with the old value, tolerance, type, and source in the owning item’s audit log.
  • delete_file: permanently deletes an attached file and all Reader values extracted from it (leaving Manual and Unknown values intact). By default, dry_run is true, so your first call previews values_to_delete without deleting anything; to execute the deletion, pass dry_run: false and confirm_hash (the file’s MD5 hash from list_files).

All four tools refuse to touch signed items, deleted items, or records attached to or cited by a hypothesis in InReview or Accepted.

Drafting and updating Wiki pages

You can also use an AI assistant to turn raw project data and literature notes into Project Wiki pages (Chapter 11: The five-section Project Wiki):

  • wiki_create_page: takes project_id, section (Goals, Ideas, Literature, Analysis, or References), title, body_md, and optional attachments (paths inside --upload-root). It idempotently creates the Wiki/ and Wiki/<section>/ folders if they do not exist yet, creates the Wiki item, and writes the .md body and any attachments.
  • wiki_get_page: downloads the page’s .md body and returns it inline as UTF-8 body_md along with item metadata and non-Markdown attachment records.
  • wiki_update_page: replaces body_md in place and optionally uploads additional attachments.

Both wiki_create_page and wiki_update_page are all-or-nothing. They validate every file type and upload-root path before writing; if any step fails, they roll back the new records and restore the previous .md body text automatically.

Preparing hypotheses and the human-in-the-loop boundary

In Chapter 10, you saw how a hypothesis links a proposal, experimental runs, cited evidence, and a conclusion across two human review gates. Through MCP, an agent can prepare every part of that record for you (Figure 18-1 and Table 18-1):

  1. Propose (propose_hypothesis and update_hypothesis): the agent creates a root or child hypothesis (statement and change) in Proposed (Needs approval) state.
  2. Wait for Gate 1 in the GUI: you (or your supervisor) read the proposal in the Desktop Hypotheses view and click Approve.
  3. Attach runs and cite evidence (attach_run and cite_evidence): once the hypothesis is Approved, the agent attaches the Run or Reference items and cites the key items, files (file_id), or values (value_id). The server records each file’s MD5 hash and each value’s stored number at citation time, and bumps the hypothesis’s integer version.
  4. Submit the conclusion (submit_conclusion): the agent calls get_hypothesis to read the current version, then calls submit_conclusion with the Markdown conclusion (including [[item:N]] links), outcome (Supported, Refuted, or Inconclusive), and version. The hypothesis moves to InReview (Needs acceptance).
  5. Wait for Gate 2 in the GUI: you (or your supervisor) inspect the cited curves and values in the Desktop GUI and click Accept to seal the conclusion.
