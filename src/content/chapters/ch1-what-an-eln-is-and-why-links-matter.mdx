When you put a number into a thesis table or a journal figure, someone will eventually ask where it came from. Perhaps your supervisor asks why one coating wore through twice as fast as another. Perhaps a reviewer asks how many indents were averaged in your hardness value, or which period thickness came out of your X-ray reflectivity fit. An electronic laboratory notebook (ELN) does its job when you can answer that question in seconds without guessing.

## The four links in every laboratory result

Every experimental number rests on a chain of four records (<a href="#fig-1-1">Figure 1-1</a>):

1. **The Sample (`Specimen`):** the physical piece or model you made, identified by its sample code (such as `261015A`).
2. **The Operation (`Procedure` or `Action`):** what you did to that sample, such as a sputter deposition, a 3D profilometer scan, a nanoindentation series, or a friction test.
3. **The Raw File:** the unaltered file written by the instrument (`.depo.json`, `.fibps`, `.mit`, `.zrw`, `.xrdml`) or by an analysis program (`.xrcx`).
4. **The Stored Number (`Value`):** the quantity, numerical value, unit, and tolerance saved on the procedure or action (for example, an indentation hardness of $5.92 \pm 0.47\,\text{GPa}$).

<Figure id="fig-1-1" number="1-1" src={`${import.meta.env.BASE_URL}/figures/fig-1-1-provenance-chain.svg`} alt="Four connected boxes showing Sample, Operation, Raw File, and Number, with the first three linked by tree structure and the fourth linked by value-level Reader or Derived provenance" caption="The four-link provenance chain for a laboratory measurement. Placing an Action under its Specimen and attaching the raw file keeps the first three links. Extracting the number through a data file reader (Reader source) or a server formula (Derived source) keeps the fourth link." />

In APS ELN, the first three links are structural. When you create an **Action** under a **Specimen** and attach the instrument file to that action, the tree itself records which sample was measured, which operation ran, and where the raw bytes sit.

## Seven months of real laboratory use

A seven-month audit of daily work in the author's thin-film and tribology laboratory measured how well these four links held up in practice (`arXiv:2610.27859`). Six researchers and one AI agent recorded 24 projects containing 1,283 items, 2,676 attached files, and 674 stored values across 7,710 audit-log writes.

The structural links held up well: measurement actions sat under their specimens and held their raw files. However, when 26 stored values across six completed studies (`T1`–`T6`) were compared against the output of APS ELN's built-in data file readers on the attached files, three things stood out:

- **13 of the 26 values** matched the current reader output of an attached file after unit conversion.
- **4 values** differed from the number the attached file gives today, for example because a reader algorithm was updated or a different evaluation interval was chosen.
- **9 values** had no reader counterpart at all. Either the source file had not been attached, a screenshot had been uploaded instead of the raw data, or the number had been typed by hand before the file existed.

<Warning title="typing numbers by hand">When you type a result by hand (`Manual` source) instead of extracting it from the attached file (`Reader` source), APS ELN cannot check that number later. If a reader version, calibration, or evaluation window changes, a `Manual` number stays unverified. Use **Extract Values** whenever a reader supports your file format.</Warning>

<GoingDeeper title="how APS ELN stores value-level provenance">

Starting in APS ELN 2.1 (notebook format 5 in Community), every stored value carries a structured source record:

- **`Reader`:** records the `file_id`, the file's MD5 hash at extraction time, the `reader_id` (such as `aps.mit` or `aps.xrcx`), and the integer `reader_version`. It also stores the emitted key name, the emitted unit, the unit conversion factor, and an optional analysis snapshot (such as ticked `.mit` indents or a selected `.zrw` cycle interval).
- **`Derived`:** records the `formula_id` (such as `wear_rate_reciprocating`), the `formula_version`, and the exact `value_id` list of the stored input values used in the calculation.
- **`Manual`:** records that a person typed or edited the number. If you edit the number or tolerance of a `Reader` or `Derived` value by hand, its source switches to `Manual` while preserving the previous reader or formula note.
- **`Unknown`:** marks legacy values created before format 5 source tracking existed.

</GoingDeeper>

## Two running examples: Study A and Study B

- **Study A (`261015A`, a BN/DLC tribological coating):** A sputter deposition (`Deposition 261015A`) produces specimen `261015A`. Four measurement and analysis actions sit below it: `Thickness 261015A` (three Filmetrics 3D step-height scans, `1.fibps`–`3.fibps`), `Indentation 261015A` (an Anton Paar UNHT nanoindentation file, `BN-DLC(261015A).mit`), and `Friction test 261015A` (a DaVinci tribometer reciprocating test, `BN-DLC.zrw`). A child action under the friction test, `Wear track 261015A`, holds three optical profiler scans across the wear scar (`wear 1.fibps`–`wear 3.fibps`). Together they hold 11 raw files, 23 `Reader` values, and 1 `Derived` wear-rate value.
- **Study B (`261014B`, a Co/C multilayer X-ray mirror):** A sputter deposition (`Deposition 261014B`) includes a plasma cleaning action (`Cleaning 261014B`) and produces specimen `261014B` (20 periods of cobalt and carbon on soda-lime glass). Under the specimen sit the X-ray reflectivity scan `XRR-1 261014B` (`XRR-1_Co-C(261014B).xrdml`) and its child analysis action `XRR fit 261014B` (`XRR-fit_Co-C(261014B).xrcx`). Together they hold 8 files and 22 `Reader` values.

## Four rules that keep your data trail unbroken

Four habits prevent every broken link found in the seven-month laboratory study:

1. **Build the whole item tree at the start of the run.** Create the **Procedure**, the **Specimen**, and every planned **Action** before you walk to the instruments. An empty action in the tree reminds you that a file is still missing. At the end of the experiment, no action should remain empty.
2. **Attach the raw instrument file, never a screenshot.** A `.png` screenshot of an XRR fit or an indentation curve cannot be re-analyzed, cannot be checked for drift, and gives zero values to a reader. Always attach the native file (`.depo.json`, `.tsv`, `.fibps`, `.mit`, `.zrw`, `.xrdml`, `.xrcx`).
3. **Keep result numbers out of file names.** Name a file after the sample code, the measurement type, and the position or counterbody, such as `BN-DLC(261015A).mit` or `wear 1.fibps`. Never name a file `351.9nm.fibps`. Results belong in stored **Values**, where they carry units, tolerances, and provenance.
4. **Extract values from files instead of typing them.** Click **Extract Values** in the viewer (or right-click several files and choose **Extract values from N files...**) so every number carries its `Reader` source. Use **Add > Derived Value...** for formula outputs.

<Remember>A file name tells you *which* sample and *which* spot was measured. A stored **Value** tells you *what number* the measurement gave.</Remember>

<InELN>To check where any stored number came from, open the **Procedure** or **Action** with **Item > Edit**, select the **Values** tab, and click the value row. The line below the list names the reader, its version, the key name, and the source file, and enables **Go to file**.</InELN>
