Part 3 · Chapter 14

Completeness, Audit, and Signatures

In This Chapter

  • Defining and running Completeness Rules for each Action Type and Equipment
  • Finding missing files and missing values with Data Completeness checks
  • Inspecting the notebook Audit Log by date, entity, operation, and user
  • Applying and verifying cryptographic Electronic Signatures (SIGNED)

Before you mark an experiment finished or hand it to your supervisor, check three things: every action has its raw file, every value matches its reader output, and the finished record is locked against edits. APS ELN checks each of these in turn (Figure 14-1).

Three layers of record integrity

Three tools handle completeness, provenance, and locking (Figure 14-1):

  1. Completeness Rules (Tools > Data Completeness...): checks whether every Procedure and Action in a project has the required raw File Types and extracted Value Types for its Action Type and Equipment.
  2. Provenance and Audit (Check Value Sources... and Tools > Audit Log...): verifies that every Reader and Derived value still matches its stored file and formula (Chapter 9: Checking value sources and understanding drift codes). It also records the chronological log of every Create, Update, and Delete event in the notebook.
  3. Electronic Signatures (Signature > Sign Item...): computes a cryptographic content hash over a finished item, marks it with a dark-red SIGNED badge, and locks it permanently against any further edits.

Completeness rules and Data Quality Checks

During a busy day at the instruments, it is easy to create a measurement action (such as a friction test or an XRR scan) and forget to attach the raw file or extract its values. Completeness Rules catch those gaps automatically across an entire project.

To define or inspect completeness rules:

  1. Choose Tools > Completeness Rules….
  2. Click Add (or select an existing rule to edit it).
  3. Enter a Title and Description, and select the matching Action Type (for example, Indentation or Tribotest), Equipment (optional), and Severity (Error or Warning).
  4. In the lower lists, tick the Required File Types (such as .mit or .zrw) and the Required Value Types (such as Hardness and Modulus, or Fn, Cycles, and COF).
  5. Tick Active and click Save.

To run a completeness check on your project before asking your supervisor for review:

  1. Select the project or folder in the Projects panel.
  2. Choose Tools > Data Completeness… (or right-click the project/folder and choose Data Quality Check… in the team client).
  3. Inspect the Data Quality Check table, which lists Category, Severity, Item, Location, Rule, and Missing (the exact file type or value type that is absent).
  4. Double-click any row (or select it and click Go To) to jump straight to the incomplete item in the main window. Attach the missing file or extract the missing value, and re-run Tools > Data Completeness… until zero issues remain. You can also click Export… to save the report as a CSV file.

Inspecting the Audit Log

Every time a person or an MCP agent creates, updates, or deletes a record in APS ELN, the notebook writes an entry to its Audit Log:

  1. Choose Tools > Audit Log….
  2. Set the optional filters at the top of the dialog: From and To dates, Entity (such as Item, File, Value, Protocol, or Hypothesis), Op (Create, Update, or Delete), and User.
  3. Click Refresh to inspect the Timestamp, Entity Type, Entity ID, Operation, User, and Description of each event.

Tip

When you delete a stored value (or when a batch reader update replaces old values), the audit log preserves the old record. It keeps the old number, tolerance, value type, source, and description in the item’s audit trail. You can always check what was removed and when.

Signing an item and verifying signature integrity

Once an item passes Tools > Data Completeness… and Check Value Sources…, you can apply an Electronic Signature to lock it permanently:

  1. In the Items panel, right-click the Procedure, Specimen, or Action itself (not an attached file or protocol row) and choose Signature > Sign Item….
  2. Check the Item Title shown in the dialog.
  3. Select the signature Meaning: Authored, Reviewed, Approved, or Witnessed.
  4. Enter an optional Comment and type your Password (the signing password you set when creating your local Community notebook in Chapter 2, or your personal account password in a team lab).
  5. Click Sign. A dark-red SIGNED badge appears beside the item in the tree.

Warning: signing is permanent and cannot be undone

Signing an item permanently locks that item against any further edits: you cannot edit its fields, attach or replace files, save working drafts, add or edit values, or delete the item. APS ELN provides no “unsign” command. Always run Check Value Sources… and Tools > Data Completeness… before you sign.

To inspect a signature and verify that the item’s database record still matches its signed hash:

  1. Right-click the signed item and choose Signature > View Signature… (or double-click the signed badge).
  2. Read the Signed By, Date, Meaning, Comment, and Content Hash fields.
  3. Click Verify Now (or right-click the item in the tree and choose Signature > Verify Integrity). APS ELN recomputes the hash over the item’s committed fields, note and protocol entries, file titles and MD5 hashes, and numeric values and tolerances. It then reports whether the hash is VERIFIED.

Going Deeper: what Verify Integrity checks and what check_storage checks

Signature > Verify Integrity checks the committed database records of that single item (including the stored MD5 hashes of its attached files), and it is not recursive over child items. To verify that every physical attachment file on disk or WebDAV still matches its recorded MD5 across a whole project, pair signature verification with the MCP check_storage tool (Chapter 16). Items signed in older versions before versioned canonical hashes existed display Legacy signature; integrity cannot be verified while remaining locked.
